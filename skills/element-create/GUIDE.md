# element-create — 정본 절차 (GUIDE)

> **이 파일이 정본이다.** 설치된 스텁이 발동 시 `npx ie guide element-create` 로 매번 이 내용을
> 새로 연다. 패키지를 업데이트하면 지침도 함께 갱신된다.
>
> 팀은 컴포넌트 디렉토리를 직접 뒤지지 않는다. UI 가 필요하면 **역할을 설명**하고, 이 스킬이
> 재사용을 먼저 제안한다. 컴포넌트는 이 스킬을 쓸 때마다 레지스트리에 축적된다.

---

## 0. 경로를 하드코딩하지 않는다

프로젝트마다 컴포넌트·레지스트리 위치가 다르다. **항상 먼저 해석된 설정을 읽는다:**

```bash
npx ie config --json
```

`elementsDir` · `entriesDir` · `importAlias` · `gallery.port` 가 여기서 나온다. 이 문서의 어떤
경로 예시도 그대로 믿지 말고 이 출력을 따른다.

설정이 없다면(`configFile: null`) 기본값으로 동작하지만, 먼저 `npx ie init` 을 제안한다.

---

## 1. intent 와 summary 를 확보한다

**intent** — 요청자의 설명(이 컴포넌트의 역할·책임)을 한 문장으로. **원문 표현을 보존한다.**
"왜 무엇을 요청했나"의 원본이라 나중에 재분석·재현의 근거가 된다.

**summary** — 그와 **별개로**, 카드·상세에 보여줄 한 줄 설명을 짓는다. intent 가 요청 맥락이 섞인
원문이라면, summary 는 누가 읽어도 이해되는 담백한 설명문이다.

> **summary 워딩 규칙 (그대로 지킨다):**
>
> - **한 문장, 담백하게.** "~입니다."로 끝나는 평서문 하나. "무엇인지 + 무엇을 하는지"만.
> - **개발자가 아니어도 이해되게.** 컴포넌트·prop·라이브러리 이름, 코드, 영문 기술용어를 넣지
>   않는다. 눈에 보이는 동작과 쓰임새로 풀어 쓴다.
> - **"—"(긴 붙임표)를 쓰지 않는다.** 괄호로 덧붙이지도 않는다. 접속사로 자연스럽게 잇는다.
> - **상투어·과장어 금지.** "~를 통해", "~를 제공합니다", "손쉽게", "직관적으로", "효율적으로",
>   "다양한" 을 뺀다. 영어 문장을 그대로 두지 말고 우리말로 다시 쓴다.
> - 예: intent `"아이콘이 회전하는 접이식 아코디언 — motion-primitives Accordion 통합 요청"`
>   → summary `"제목을 누르면 한 칸씩 펼쳐지는 접이식 목록입니다."`

## 2. 재사용을 먼저 찾는다

```bash
npx ie element list --json
npx ie element list --query "<역할 키워드>" --json
```

- 역할·키워드로 후보 2~3개를 고르고, 필요하면 `npx ie element get <name> --json` 으로
  props·intent 를 자세히 본다.
- **`Composite` 와 `Animations` 를 우선 본다.** `System` 은 기반 요소라 역할이 겹치는 경우가 드물다.
- `Animations` 를 볼 때는 **독립 위젯**(자체 모달·포털·수명주기를 소유)과 **이식 가능한 동작**
  (다른 요소에 얹는 효과)을 구분한다. 요청이 후자면 대상 컴포넌트를 새로 만들 필요가 없다.

## 3. 매칭을 판단한다

**역할이 겹치거나 기존 props/variant 확장으로 흡수 가능하면 → 기존 것을 추천한다. 새로 만들지 않는다.**

- 추천 응답에는 **편집 가능한 props 요약**을 함께 낸다(`이름:타입`, enum 이면 옵션까지).
  요청자가 "무엇을 바꿀 수 있는지"를 바로 알아야 확장으로 해결할지 판단할 수 있다.
- import 예시를 함께 준다: `import { X } from "<importAlias>/<name>"`.
- **추천했으면 반드시 기록한다:**

  ```bash
  npx ie element log <추천한이름> --action recommended --prompt "<요청 원문>"
  ```

  코드를 안 고쳤어도 이것만은 남긴다 — 없으면 이 하네스의 존재 이유인 **재사용률**을 영영 잴 수 없다.

- 신규 요청이 기존 컴포넌트와 역할이 **70% 이상 겹치면** 신규 생성 대신 그쪽 확장을 제안한다.

## 4. 매칭 실패일 때만 새로 만든다

```bash
npx ie element new <name> \
  --intent "<요청 원문 그대로>" \
  --summary "<§1 규칙대로 지은 한 문장>" \
  --category Composite \
  --keywords "한글,키워드,english,keywords"
```

- `<name>` 은 kebab-case (`stat-card`). 역할이 드러나는 이름으로.
- `--category` — `Composite`(완성형 조합) · `Animations`(움직임) · `System`(기반 요소).
- `--keywords` 는 **한글과 영문을 함께** 넣는다. 검색이 부분 문자열 매칭이라 둘 다 있어야 찾힌다.
- 긴 원문은 `--intent-file <경로>` 로 준다(개행·코드펜스가 보존된다).

이 명령이 3파일 + 엔트리 + `created` 이력 + 인덱스를 한 번에 만든다. **그다음 실제 구현으로 채운다:**

| 파일 | 채울 내용 |
| --- | --- |
| `<name>.tsx` | 진짜 컴포넌트. 스캐폴드는 자리표시다 — 요청한 역할대로 다시 쓴다. |
| `<name>.demo.tsx` | 갤러리 프리뷰 한 컷. props 없이 스스로 그려져야 한다. |
| `index.ts` | 그대로 둔다. |

**데모 규칙** — 카드 프레임이 작다. 대표 상태 **하나만** 담고, 타이머(`setInterval`/`setTimeout`)·
`requestAnimationFrame`·루핑 애니메이션을 넣지 않는다. 목록에서 카드 수십 개가 동시에 움직이면
읽을 수가 없다.

**props 를 실제로 넣었으면 엔트리에도 반영한다** — `entriesDir/<name>.json` 의 `meta.props` 에
`{ name, type, editable }` 배열로 적는다. 자유 문자열이 아니다. 이 스키마가 있어야 나중에 페이지
조립이 실 컴포넌트를 그린다. 선택 결과를 알리는 콜백은 `type: "action"` 으로 선언한다.

마지막으로 인덱스를 갱신하고 **검증 게이트를 통과시킨다**:

```bash
npx ie index
npx ie element schema <name>     # TS Props → meta.props 백필
npx ie element validate <name>   # 하드룰 검증 — 차단이 있으면 완료 처리하지 않는다
```

## 5. 하드 룰 (위반 시 완료 처리하지 않는다)

1. **색은 `st-*` 토큰만.** 임의 hex/rgb/hsl/oklch 리터럴 금지.
   쓸 수 있는 토큰 목록은 `npx ie config --json` 의 `tokens.css` 파일에서 확인한다.
2. **크기·여백·라운드는 스케일만.** radius 는 `rounded-{xs,sm,md,lg,xl,full}`, 폰트는
   `text-step-{n2,n1,0,1,2,3}`, 간격은 Tailwind 기본 스케일. `w-[13px]` 류 임의값 금지.
3. **필요한 토큰이 없으면 코드에 값을 박지 말고 사용자에게 알린다.** 팔레트를 늘리는 건 디자인
   결정이지 구현 결정이 아니다.
4. **엔트리와 코드는 항상 쌍이다.** `ie element new` 를 거치지 않고 파일만 만들지 않는다.
5. **`summary` 없이 완료하지 않는다.**
6. **데모 없이 완료하지 않는다.** 데모가 없으면 갤러리 카드가 비고, 페이지 조립에서도 쓸 수 없다.

## 6. 딥링크는 **확인한 뒤에만** 준다

> ⚠️ 딥링크를 주는 것과 딥링크가 뜨는 것은 다르다. 갤러리는 SPA 라 `/c/<없는이름>` 에도 서버가
> 무조건 200 을 준다 — "찾을 수 없습니다"는 **브라우저에서만** 뜬다.
>
> ⚠️⚠️ 그리고 **같은 포트를 다른 프로젝트의 갤러리가 점유하고 있을 수 있다.** 그쪽 레지스트리에
> 우연히 같은 이름이 있으면(`button`·`card` 같은 흔한 이름은 실제로 흔하다) 엔트리 조회가 200 을
> 돌려준다 — 내 컴포넌트는 등록도 안 됐는데 "확인됨"이 되는 **위양성**이다.
>
> 그래서 직접 curl 하지 말고 아래 한 명령을 쓴다. 신원(어느 프로젝트의 갤러리인가)을 먼저 보고
> 엔트리를 그다음에 보므로 이 함정이 구조적으로 막힌다.

```bash
npx ie gallery status <name>
```

| 출력 | 뜻 | 어떻게 말할 것인가 |
| --- | --- | --- |
| `✓ 확인됨 — …/c/<name>` | 내 프로젝트의 갤러리가 이 엔트리를 본다 | 딥링크를 **"확인됨"** 으로 전달 |
| `! … 이 없습니다` | 갤러리는 맞는데 엔트리가 없다 | `ie index` 를 실행했는지·이름이 맞는지 확인 |
| `✗ 다른 갤러리가 쓰고 있습니다` | 그 포트는 **남의 프로젝트**다 | 이 포트의 응답을 근거로 삼지 않는다. `ie gallery --port <다른포트>` 안내 |
| `! 실행 중이 아닙니다` | 갤러리 미실행 | 링크는 주되 반드시 **"미검증"** 이라고 명시 |

**어떤 경우에도 "확인됨"처럼 말하려면 위 명령이 `✓` 를 낸 뒤여야 한다.**
**스킬은 갤러리를 백그라운드로 띄우지 않는다** — 어느 프로젝트의 갤러리가 그 포트를 쥐고 있는지
아무도 모르게 된다.

**응답 말미 (항상 · 이걸로 끝맺는다):**

```text
── ✦ instant-elements ──────────────────────────────

   <name>   ·  <category> · <status>

   🔗  갤러리   http://127.0.0.1:<port>/c/<name>        ← 확인됨 / 미검증 을 함께 적는다

   ▸  다음 단계
      수정하려면  "<요청> 수정해줘"  (이력은 자동으로 남긴다)

────────────────────────────────────────────────────
```

## 7. 기존 컴포넌트를 고칠 때

1. **코드가 어디 있는지 엔트리에서 확인한다** — 경로를 가정하지 않는다.

   ```bash
   npx ie element get <name> --json    # entry.files[0].path
   ```

2. 그 디렉토리 **안에서만** 고친다. 데모(`*.demo.tsx`)도 함께 맞춘다 — 갤러리 카드가 그 파일을 그린다.
3. props 나 export 이름이 바뀌었으면 엔트리(`meta.props` · `meta.exportName` · `meta.usage`)도
   같은 작업에서 갱신한다.
4. **코드 변경을 먼저 커밋한다.** 이 커밋의 SHA 가 곧 복원 지점이 된다.
5. **이력을 남긴다:**

   ```bash
   npx ie element log <name> --action modified \
     --note "<무엇을 바꿨는지 한 줄>" \
     --prompt "<요청 원문 그대로>" \
     --sha "$(git rev-parse HEAD)"
   ```

   긴 원문은 `--prompt-file <경로>` 로 준다. **이 단계를 건너뛰지 않는다** — 기록이 없으면
   "누가 왜 이렇게 바꿨나"를 다음 사람이 코드에서 역추적해야 한다.

## 8. 입출력 요약

- **읽기**: `ie config --json` · `ie element list/get --json`
- **쓰기(신규)**: `ie element new` 가 만든 3파일을 실제 구현으로 채우고, 엔트리 `meta.props` 보강
- **쓰기(수정)**: 엔트리가 가리키는 실제 코드 위치 + `ie element log`
- **실행**: `ie index` (엔트리를 손으로 고쳤으면 반드시)
